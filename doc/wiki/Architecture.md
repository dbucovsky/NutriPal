# Architecture

## Stack

- **Backend:** PHP, exposing a JSON API. Locally this runs via PHP's built-in dev server (`php -S localhost:8080 -t public`, started with `start-services.ps1`/`start-services.bat`), not Apache — XAMPP is used only for MySQL locally. Apache/cPanel is the target in production (Bluehost).
- **Database:** MySQL (via XAMPP locally; Bluehost-managed MySQL in production).
- **Frontend:** React SPA, calling the PHP JSON API.
- **Auth:** Real login (not "whoever's on localhost is me") is designed in from the start, since remote deployment is a planned next step even though not day one.
- **Secrets:** Environment-based, not committed — see `doc/credentials/` for local-only reference notes.

## Why this stack

NutriPal is intended to eventually run on a Bluehost shared hosting plan, which is PHP/MySQL/Apache-native via cPanel. Bluehost's Python/Node support (where available) runs through cPanel's Passenger integration in WSGI mode and doesn't support always-on background processes — a poor fit for FastAPI (ASGI) and for any continuous sync/analysis process. PHP + MySQL avoids all of that friction and matches the local XAMPP dev environment exactly, so there's no dev/prod parity gap.

The app's analysis needs (macro/micronutrient math, activity/weight correlation) are arithmetic over a single user's modest dataset — not heavy enough to need Python's data-science ecosystem (pandas etc.), so giving that up costs little.

React was chosen over server-rendered PHP views specifically because fast meal logging (near-identical daily meals with small tweaks) is a first-class feature, not an afterthought — that UX benefits from a proper SPA rather than full-page form submissions.

## Frontend (dev setup, done 2026-09-08)

The React app lives in `frontend/` (scaffolded with Vite, plain JavaScript — no TypeScript yet). It runs as its own dev server, separate from the PHP one:

```
cd frontend
npm install   # first time only
npm run dev   # http://localhost:5173
```

`frontend/vite.config.js` proxies any `/api/*` request to `http://localhost:8080` (the PHP dev server), so the app can just `fetch('/api/...')` with no CORS handling needed in dev. The PHP side of the API lives under `public/api/` — one file per endpoint (`login.php`, `food-log.php`, `heart-rate.php`, `sleep.php`, `exercise.php`, `weight.php`, `run-sync.php`, `sync-runs.php`, `import-hc.php`), matching this project's existing one-file-per-concern style rather than a router/framework. `food-log.php`/`sleep.php`/`exercise.php`/`weight.php`/`heart-rate.php` all share `src/LocalDay.php` for both single-day and multi-day range bucketing (see below). Not wired into `start-services.ps1` yet (that script is XAMPP/PHP-specific per its own header) — start the frontend dev server separately for now.

There's a placeholder login (`public/api/login.php`, `frontend/src/components/Login.jsx`) with no password/session/security of any kind — it just looks up a real user by email and the frontend remembers the result in `localStorage`. It exists purely to give the frontend a real "current user" concept and exercise a POST round-trip; real authentication is still future work (see "Auth" above).

**Pages so far** (a simple tab switcher in `App.jsx`, no router library yet): Food, Heart Rate, Sleep, Exercise, Weight, Steps — every tab now understands the full Day/Week/Month/Year/Custom view-mode selector, so `App.jsx` no longer needs a day-only-tab special case (removed 2026-09-10 once Sync, the only tab that ever needed it, moved into the menu — see below). Navigation state is a single `view` object (`{type, date, endDate}`) lifted to `App.jsx` and shared across every tab, via `frontend/src/components/DateNav.jsx` + `frontend/src/dateUtils.js` (local-day-safe date math, formatting per view type, and converting the API's UTC datetime strings to the viewer's local time for display). `DateNav` shows prev/next arrows (stepping by whatever the current view's period is — a day, a week, a month, a year) flanking a "Weekday DD-MMM-YYYY"-style label that opens the browser's native date picker against a visually-hidden real `<input type="date">`, plus the Day/Week/Month/Year/Custom view-mode selector. Heart Rate uses `chart.js`/`react-chartjs-2` (the frontend's first real dependency beyond React itself) for a day's bpm trend — the API pre-buckets raw readings into 10-minute averages server-side (`public/api/heart-rate.php`) rather than shipping tens of thousands of raw points to the browser. That per-day chart query is skipped entirely for ranges over 10 days (Month/Year/long Custom) — those views render every day collapsed by default (see `MultiDay.jsx` below) so the chart is never seen without expanding a day first, and computing it live for hundreds of days turned out to be the single most expensive part of the endpoint (see the perf note below). Every collapsible day (and, on Food, meal) section shows aggregated stats — daily totals, avg/resting bpm, total sleep duration, session counts, etc. — directly in its always-visible summary line via `MultiDay`'s `renderSummary` prop, so collapsing something doesn't hide the one thing worth knowing about it at a glance. Weight reuses the same chart.js dependency for a trend line across whatever range is selected (only shown once a range has 2+ readings) — plotted on a linear axis over each reading's real epoch timestamp rather than a true time scale, since no date adapter is installed; a tick/tooltip callback formats it back to a readable date instead. Steps (`public/api/steps.php`, 2026-09-10) shows a `chart.js` bar chart of daily totals — `steps_readings` has a real, still-open cross-source duplication problem (see `doc/wiki/Database-Schema.md`'s Open Items), so each day's bar is whichever single `data_source_id` reported the most steps that day, not a naive sum; the other sources seen that day are shown but discarded, in the UI for transparency. Sync (`frontend/src/components/Sync.jsx`, no date — see `doc/wiki/Data-Sync.md`) triggers `sync-google-health.php` and `import-health-connect.php` synchronously and shows their captured output — no longer a tab (see the ribbon menu note below), but otherwise unchanged.

**Top ribbon** (2026-09-10): a `MenuDropdown.jsx` hamburger button on the left of `.app-header` (click-outside-to-close via a `mousedown` document listener, no new dependency) replaced the old standalone Log out button with a menu — Log out, Settings, Help, Sync, About. Settings/Help/About are minimal static-content popups (`InfoPanels.jsx`, reusing `Popup.jsx`) rather than real functionality that doesn't exist yet; About's version line comes from a new `public/api/version.php` (parses the first `## Vx.y.z` line out of `CHANGELOG.md`) instead of a hardcoded string that would go stale on the next bump. Sync, selected from the same menu, opens the existing `Sync` component inside `Popup.jsx` too. Next to the menu, `QuickSyncButton.jsx` is a single green icon that runs `runSync({ mode: 'live' })` with no `days`/`full` override — this app has no true "time since last sync" tracking (see `scripts/sync-google-health.php`'s own docblock), so the already-established fixed-7-day incremental mode, with its existing dedup rules, stands in for it; the icon spins/disables while in flight and shows a transient synced/error message, leaving the full progress panel and output log in the menu's Sync popup for anyone who wants it. `MenuDropdown`/`Login` interaction: `App()` still full-screens `Login` whenever there's no current user (see below), so the menu is only ever reachable while logged in — it always shows "Log out"; there's no reachable "Log in" state to wire up.

The Heart Rate chart also overlays sleep and exercise periods as shaded background bands (`chartjs-plugin-annotation`), so you can see e.g. a heart-rate spike lining up with a walk, or the overnight low lining up with sleep. This needed the x-axis to switch from category labels to a linear "minutes since local midnight" scale (0–1440) so overlay boxes and the bpm line share one coordinate system; `heart-rate.php` returns `exercise_periods`/`sleep_periods` clipped to that same [0, 1440] range (a sleep session starting the evening before gets clipped to start at 0) using an *overlap* query (does the session touch this day's window at all), which is a different, looser rule than `exercise.php`/`sleep.php`'s own single-page day-assignment rules.

**Heart Rate range-query performance**: computing a Year view's per-day summary/HRV aggregates the naive way (a separate query per calendar day, needed for DST-correct local-day boundaries — see `LocalDay.php` below) took ~14.5s end to end for a real year of data, from ~1,800+ sequential round trips rather than any one query being slow. Batching every day into a single query via a day-boundaries-derived-table JOIN looked like the right fix but was confirmed directly to be much worse — MySQL evaluated every raw reading row against every day's bounds with no usable index, and the query was still running 2+ minutes later (killed via `KILL <thread_id>` on the hung connection, found via `SHOW PROCESSLIST`). The fix that actually worked: a single `UNION ALL` of independent per-day aggregate subqueries, each keeping its own simple indexed `WHERE reading_time >= ? AND reading_time < ?` range — same per-query cost as before, merged into one round trip. That brought a full year down to ~11s; the remaining cost is real (exact MIN/MAX/AVG/COUNT over several million raw readings can't be answered from an index alone) and would need a precomputed daily-rollup table to fix properly — not done, tracked as a known limitation.

**`src/LocalDay.php`** centralizes the local-day-bucketing logic (see the "Frontend (dev setup...)" note above and `doc/wiki/Data-Sync.md`) so every endpoint computes it identically instead of repeating the same `DateTimeImmutable`/`DateTimeZone` dance. Sleep uses a different bucketing rule than the other three: a session is shown on the day it *ended* (the "woke up on this day" convention), not the day it started, since sleep sessions usually span midnight. `resolveRange()` (added alongside the original single-day `resolve()`) computes a Sunday-Saturday week / calendar month / calendar year / arbitrary custom range as one UTC window — still a single indexed range query, not a per-day loop — and `toLocalDate()` converts a result row's own UTC timestamp back to its local calendar date so `food-log.php`/`sleep.php`/`exercise.php`/`weight.php` can group one range query's rows into a `days[]` array. `view=day` still produces a one-day `days[]` array, so the frontend has exactly one rendering path (`frontend/src/components/MultiDay.jsx`) regardless of which view is active.

**`MultiDay.jsx`** (2026-09-10) recursively groups a range's days into year → quarter → month → week → day, collapsible at every level, rather than one flat list of day-sections — a Year view now shows a handful of collapsed quarters instead of up to 365 day-sections. Any level that would only produce a single group for the requested range is skipped entirely (pure string-key grouping via `dateUtils.js`'s `weekKey`/`monthKey`/`quarterKey`/`yearKey`, no `Date` object), so a Week view falls straight through to the original flat day list with no change in behavior. Day-level sections still take an optional `renderSummary(day)` prop rendering aggregated stats into the always-visible summary line (daily macro totals, avg/resting bpm, sleep duration, session counts, weight range, step count/source) — coarser year/quarter/month headers show only a label, not an aggregate, since that would need real per-page aggregation work not built here.

**Session-scoped heart rate popups**: Exercise sessions, and the exercise periods the Heart Rate page already overlays as shaded bands on its day chart, both get a small chart-icon button (`SessionHrPopup.jsx`) that on click fetches and shows that exact session's own bpm curve (x-axis = elapsed minutes since the session started) from a new `public/api/heart-rate-range.php?user_id=&start=&end=` endpoint — raw, unbucketed readings for one specific UTC window (a session is minutes to a couple hours, so this stays small), distinct from `heart-rate.php`'s whole-day/range view. A shared `Popup.jsx` (minimal modal) backs this and the Food pie-chart popup below.

**Food's macro display** (`FoodLog.jsx`, 2026-09-10): `MacroRow` renders kcal/protein/carb/fat as a fixed 7-column CSS grid (`kcal-value | "P" | value | "C" | value | "F" | value`) instead of inline text, so digits line up down the page regardless of label width — the same component/column template backs per-entry rows, meal summaries, day summaries, and the footer totals. The day-level totals (footer and the `MultiDay` summary line) are clickable per metric, opening a `Pie` chart of that macro's per-food contribution that day (grouped by name+brand, computed client-side from the already-fetched day data). The day-summary click sits inside a native `<summary>`, so it needs `stopPropagation()`/`preventDefault()` to avoid also toggling that day's collapse state.
