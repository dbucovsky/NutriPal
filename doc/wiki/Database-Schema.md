# Database Schema

Defined in [`sql/schema.sql`](../../sql/schema.sql) (checkpoint — see status note below), with sample data in [`sql/sample_data.sql`](../../sql/sample_data.sql). General, project-agnostic schema patterns used throughout (naming, history/audit, ownership, dedup, non-destructive corrections) are documented separately in [[Database-Design-Patterns]] rather than repeated here — this page covers what's specific to NutriPal's own tables.

**Status**: every table has now had its own detailed table-by-table review pass grounded in real API/Takeout data (not just the original pre-review draft shapes) and is considered final-for-now. Still open: the deferred cross-source reconciliation logic (upsert priority, `mixed`-conflict resolution) noted throughout — see Open Items below.

**Two schemas**: `sql/schema.sql` creates and populates two databases — `nutripal` (every live/data table) and `nutripal_hist` (every `_hist` audit table, see [[Database-Design-Patterns]]) — so history, which grows much faster than live data, can be backed up/archived on its own cadence. **Before running this file against the real Bluehost database**, every `nutripal_hist` occurrence must first be replaced with the actual prefixed database name (Bluehost's cPanel prefixes all database/user names for this account, e.g. `theshaf2_nutripal_hist`) — the hist schema name is baked literally into every trigger body, since raw SQL can't parameterize identifiers. This is a manual step per deploy, documented in the schema file's header.

## Two ingestion sources, one dataset

NutriPal ingests the same underlying data two ways:
- **`google_health_api`** — live incremental sync (last 7 days rolling, see [[Data-Sync]])
- **`google_takeout`** — a bulk export file (Google Takeout → Google Health), used to (1) quickly initialize a new user with full history instead of paging through years of API calls, and (2) periodically re-check that the API sync hasn't silently missed anything

Both sources write into the same tables, distinguished by `ingestion_source_id` (a lookup, not the raw `data_source` column — see below) plus a `fingerprint` for dedup (see [[Database-Design-Patterns]] for the general dedup mechanism). Two more values exist beyond the two sources themselves:
- **`mixed`** — reserved specifically for a genuine structural conflict between the two sources for what identity-resolution determined is the same logical entry — e.g. the API reports a 7oz serving, Takeout reports 8oz, for what's otherwise clearly the same food log entry. Only for **time-of-consumption** and **quantity/serving-size** disagreements — never for nutrient values (that's the `SRC`/`FIX`/`MOD` mechanism instead) and never for one source simply filling in a field the other left blank (that's an ordinary upsert).
- **`nutripal`** — the row was created directly in the app (the future custom/repeat meal logging feature), not synced from Google at all. Not named "manual" — Google's own `data_source` field already uses the value `MANUAL` for a different meaning (the user hand-entered data into the Fitbit/Google Health app itself), and reusing that word here would be confusing next to it.

**`data_source` vs. `ingestion_source` vs. `recording_method`** — three easy-to-confuse, deliberately disambiguated concepts: `data_source_id` (→ `lut_data_source`) is which app/device *Google Health itself* says recorded the entry (e.g. "Fitbit App," "Charge 5") — pass-through metadata from the source data. `ingestion_source_id` (→ `lut_ingestion_source`) is which of *NutriPal's own* ingestion pipelines wrote the row — our own bookkeeping, described above. `recording_method_id` (→ `lut_recording_method`, added during the steps/heart-rate/measurements/exercise/sleep review) is *how* the reading was captured — `ACTIVELY_MEASURED`/`PASSIVELY_MEASURED`/`MANUAL`/`DERIVED`, present on the live API's `dataSource.recordingMethod` for every data type checked, and on Takeout's exercise `logType` field. Present on `steps_readings`, `heart_rate_readings`, `heart_rate_variability_readings`, `daily_resting_heart_rate`, `measurements`, `exercise_sessions`, and `sleep_sessions` — nullable everywhere, since most Takeout CSV formats (steps/heart-rate/weight) don't carry it at all. **Gotcha confirmed in real data**: Takeout's `UserSleeps.csv`/`UserSleepStages.csv`/`UserSleepScores.csv` each have their own "data_source" column, but for these three files only it actually reports the recording method (`MANUAL`/`DERIVED`/`ACTIVELY_MEASURED`/`PASSIVELY_MEASURED`) — not a device/app name like every other Takeout file — so it maps to `recording_method_id`, not `data_source_id`.

**`api_uid`** — the live API's native ID for a row, when the API has touched it. Distinct from Takeout-native IDs, which have their own dedicated columns (`log_id` on `exercise_sessions`; `sleep_id`/`sleep_stage_id` on `sleep_sessions`/`sleep_stages`). Confirmed which Takeout categories actually carry a native ID: **nutrition, steps, heart rate, and weight Takeout files have no ID column at all** (verified against the readme field lists) and rely purely on the fingerprint; only exercise and sleep Takeout data carry stable native IDs. `api_uid` has its own unique key (`UNIQUE(user_id, api_uid)`) and takes priority over fingerprint matching during identity resolution — see [[Database-Design-Patterns]] for why (a food entry's logged time can be edited after the fact, which changes its fingerprint but not its `api_uid`).

## Fingerprint composition

Per table, the fields hashed into `fingerprint` (sha256, computed identically regardless of source):
- `food_log_entries`: `start_time`, `end_time`, `food_name` (lowercased/trimmed), the **meal type's name** resolved through `lut_meal_type` (not its id — ids can differ across environments/seed order, the name is stable), `brand_name` (lowercased/trimmed, empty string if null). Nutrient values are excluded — float rounding differences between sources shouldn't break matching.
- `steps_readings` / `heart_rate_readings` / `heart_rate_variability_readings`: `reading_time` + the reading's value (steps, bpm, or rmssd_ms respectively), compared at minute precision. **Confirmed via real data that this alone isn't enough to prevent double-counted daily totals** for steps: multiple devices (e.g. a wearable and a phone) can both report overlapping step activity independently, each internally consistent and each passing fingerprint dedup on its own — see the multi-device note under Open Items.
- `daily_resting_heart_rate`: no fingerprint at all — the natural key **is** `(user_id, reading_date)`, since Google computes at most one resting-HR figure per user per day. A resync that recalculates the value is a plain `UPDATE` on the existing row, not a new fingerprint.
- `measurements`: `reading_time` + the **measurement type's name** (resolved through `lut_measurement_type`, same name-not-id reasoning as meal type) + `value`. Including the type name is essential — a blood-pressure systolic and diastolic reading legitimately share the same `reading_time`, and would otherwise collide.
- `exercise_sessions`: `log_id` when a native ID is available (Takeout's Fitbit `logId`); otherwise `start_time` + `activity_name` (lowercased) + `duration_ms`.
- `sleep_sessions`: `sleep_id` when available (Takeout); otherwise `start_time` + `end_time`.
- `sleep_stages`: `sleep_stage_id` when available (Takeout); otherwise `sha256(sleep_session_id|start_time|end_time|stage type name)`, scoped to the session so identical stage durations on different nights never collide. **This fallback is required, not hypothetical** — confirmed via real data that the live API's embedded `sleep.stages[]` and Takeout's legacy `sleep-*.json` `levels.data[]` both provide stage-level detail with no native ID at all; only Takeout's `UserSleepStages.csv` has one.
- `foods_db`: `name`, `brand_name`, `dimension`, and `COALESCE(version, 0)` — lets the same food name exist multiple times (once per version) without colliding, while still deduping a true re-import of an identical version. Unique key is `(user_id, group_id, fingerprint)` — see the ownership model below.

## Tables

**Food log** (reviewed, final for now):
- `food_log_entries` — one row per logged food event. `start_time`/`end_time` always differ by exactly 1 minute (confirmed against 6,234 of 6,235 real Takeout rows) — not a real duration, just how Google's interval-shaped data model represents a single moment. Kept as two columns to match Google's own model; any code creating new entries must follow the same convention. `energy_kcal`, `total_protein_g`, `total_carbohydrate_g`, `total_fat_g` are promoted to top-level columns (protein alongside carb/fat for macro symmetry, even though the live API only exposes carb/fat at its own top level — protein is buried in the nutrients array there, same as sodium/sugar/etc.). `is_energy_estimated` is set when Takeout-sourced rows have their energy computed from macros (4×protein + 4×carb + 9×fat) rather than reported directly, since Takeout's `nutrition_log.csv` has no energy field at all. `has_nutrient_overrides` is a cached flag (not computed on the fly) set whenever any `FIX`/`MOD` nutrient row exists, so a UI can flag "this has been enhanced" without scanning the nutrients table on every render. `food_id` (nullable) → `foods_db` links the entry to the specific catalog version it was logged from, if any — most Google-synced entries won't have one unless a future matching pass links them. Nutrition stays a logging-time snapshot regardless (never live-joined), so re-versioning a catalog food never rewrites past logs; `food_id` exists purely for traceability and "log this again."
- `food_log_nutrients` — one row **per nutrient per value type** (up to 3: `SRC`/`FIX`/`MOD`, see [[Database-Design-Patterns]]) per entry, since both the nutrient set and whether it's been corrected vary per entry. `nutrient_id` → `lut_nutrient`, deliberately curated (a nutrient not already in the lookup is dropped at ingest time, not auto-added — see the design-patterns doc's "curated allowlist" note). `unit_id` → `unit_conversions`, the same single source of truth used for serving units, extended with milligram/microgram so nutrient-scale units don't need a separate concept.

**`food_log_entries` ↔ `foods_db` linkage (resolved)**: `food_log_entries.food_id` (nullable FK → `foods_db.id`) records which catalog row, if any, an entry was logged from. The quantity multiplier needs no new column — it's already derived from `serving_amount`/`serving_unit_id` (resolved via `lut_serving_unit` to either a `unit_conversions` row or a `foods_db_custom_units` row, either of which yields a total amount in grams/mL) against `foods_db`'s per-100 nutrition. One app-level invariant, not DB-enforced: if `serving_unit_id` resolves to a `foods_db_custom_units` row, that row's own `food_id` must match `food_log_entries.food_id`.

**Steps & heart rate** (reviewed, final for now) — simple timestamped readings, each with its own `data_source_id`/`recording_method_id`/`ingestion_source_id`/`api_uid`/`fingerprint` cluster:
- `steps_readings` — real API data confirmed each point is a fixed 1-minute incremental count (not cumulative); real Takeout data confirmed irregular-interval incremental counts from **multiple devices simultaneously** (a wearable and a phone both logging the same real-world steps independently). Naively summing all rows for a daily total would double-count — see Open Items.
- `heart_rate_readings` — continuous point-in-time bpm samples.
- `heart_rate_variability_readings` — a genuinely different metric (RMSSD in decimal milliseconds, `DERIVED`), far fewer samples per day than continuous bpm. Not modeled until this review surfaced it as a distinct, real-data-backed metric.
- `daily_resting_heart_rate` — one `DERIVED` value per calendar day, keyed by `(user_id, reading_date)` rather than a fingerprint (see above). `calculation_method_id` → `lut_heart_rate_calc_method` (only `WITH_SLEEP` observed so far).

**`measurements`** (reviewed, final for now) — a single generic table for point-in-time scalar body metrics (weight, height, blood pressure, body fat %, etc.), replacing what would otherwise be a separate table per metric: `measurement_type_id` (→ `lut_measurement_type`), `value`, `unit_id` (→ `unit_conversions`, extended with length/pressure/ratio dimensions for height/blood-pressure/percentages). A multi-value reading like blood pressure is two rows (`blood_pressure_systolic` + `blood_pressure_diastolic`) sharing one `reading_time`, paired back together by the app. Confirmed the live API gives weight/height readings a genuine native per-point ID (`api_uid`), unlike steps/heart-rate — real native-ID-priority matching applies here, not just fingerprint fallback.

**`exercise_sessions`** (reviewed, final for now) — core fields as columns (`activity_type_id` → new `lut_activity_type`, resolving two disjoint raw vocabularies: Takeout's Fitbit-legacy numeric `activityTypeId` and the live API's string `exerciseType`; `distance_unit_id` → `unit_conversions`, since Takeout genuinely varies distance units while the API always reports millimeters; `has_gps` promoted to a real column, present in both sources). Heart-rate zones, active-zone-minutes breakdown, and GPS detail stay in a `raw_details` JSON column rather than fully normalized (available for later use, not modeled as separate tables in V1). `device_name` (a pre-review draft column) was removed — confirmed redundant with `data_source_id`, which already captures the same concept everywhere else.

**`sleep_sessions`** (reviewed, final for now) + **`sleep_stages`** (genuinely one-to-many, kept normalized for stage-duration trend analysis): `sleep_type_id` → new `lut_sleep_type` (`CLASSIC`/`STAGES`, confirmed identical vocabulary in both sources). Score columns (`overall_score`/`duration_score`/`composition_score`/`revitalization_score`) are `DECIMAL(6,2)`, not the originally-drafted `TINYINT UNSIGNED` — **a real bug caught by this review**: actual Takeout values are floats (e.g. `83.364879702283261`) and use `-1` as a "not computed" sentinel (translated to `NULL` at ingest, since an unsigned integer type could hold neither). Confirmed the live API's sleep response has **no score fields at all** — scores only ever come from Takeout. Extended sleep-quality fields (`minutes_longest_awakening`, `minutes_to_persistent_sleep`, `efficiency`, `main_sleep`) promoted to real columns; rarer/computable-from-stages sub-metrics (`sleep_goal_minutes`, `waso_count_*`, `restlessness_normalized`, `hr_below_resting_hr`, `deep_sleep_minutes`, `rem_sleep_percent`, algorithm version, short-awakening micro-events) live in a new `raw_details` JSON column, mirroring `exercise_sessions`' promoted-columns-vs-JSON split. `sleep_stages` gained `ingestion_source_id` and `fingerprint` — a real gap, not just an enhancement (see fingerprint composition above).

**`foods_db` family** (reviewed, final for now) — the user's own + historically-encountered food catalog, motivated by how the user actually eats (mostly home-cooked, buying ingredients in bulk and eating them across several meals) and by the API not exposing any way to search Google's own food data — only what's already been logged is visible:
- `foods_db` — nutrition always normalized per 100 units of the food's `dimension` (100g or 100mL), matching label convention, so scaling to whatever quantity/unit was actually used is always the same math. Three-tier ownership (universal / group / user) via `group_id`/`user_id`, and `version` for tracking that packaged foods' real nutrition can drift over time (different manufacturers/resellers/reformulations) — both patterns detailed in [[Database-Design-Patterns]].
- `foods_db_custom_units` — per-food named units beyond the universal standard ones (e.g. "small/medium/large orange," "18in pie slice"), one of which can be flagged `is_default`. Tied to one specific `foods_db` row (one version) — not automatically shared across other versions of the same food.
- `foods_db_nutrients` — same shape and `SRC`/`FIX`/`MOD` model as `food_log_nutrients`, for the catalog. Sets up a future enrichment workflow: a catalog food's supplementary nutrients (things Google never reports, e.g. specific amino acids) can eventually flow into a matched Google-sourced log entry — the matching logic itself is deferred to implementation time.
- `foods_db_last_used` — per-`(user, food)` usage tracking, kept separate from `foods_db` to isolate high-churn writes. `score` is a bounded, self-decaying recency-weighted frequency (not a plain lifetime counter, which would fade too slowly once a food is abandoned after heavy use) — see [[Database-Design-Patterns]] for why, and the exact write-time decay algorithm (order matters: decay must be computed from the *old* `last_used_at` before it's overwritten). `last_serving_amount`/`last_serving_unit_id` cache the quantity actually logged last time (display/prefill only, not part of the ranking) so "log again" can default to the same serving.
- `unit_conversions` — universal mass/volume unit conversions, shared by both `foods_db` and nutrient quantities.
- `lut_serving_unit` — resolves a logged serving unit to either a standard `unit_conversions` row or a food-specific `foods_db_custom_units` row (see [[Database-Design-Patterns]]'s "resolving a could-be-one-of-several-tables reference" pattern).

**Multi-user readiness** (schema shape only — no login/registration UX exists yet; the app still just operates as one hardcoded user): `users`, `groups`, `link_user_group` (membership + per-user group-priority ranking). Every user-owned table carries `user_id` directly, including child tables, and every uniqueness constraint is scoped per-user. Full rationale in [[Database-Design-Patterns]].

## Google Takeout export format (observed, 2026-09-05)

A Takeout "Google Health" export unpacks into several differently-shaped areas — this isn't one uniform format:

- **`Physical Activity_GoogleData/`** — one folder of per-month CSVs per data type: `steps_YYYY-MM-DD.csv`, `heart_rate_YYYY-MM-DD.csv`, `distance_...`, etc. Each row is just `timestamp, value, data source`. `nutrition_log.csv` and `weight.csv` are exceptions — single all-history files, not split by month.
  - Nutrition row: `start time, end time, brand name, food name, meal type, nutrients, data source` — nutrients arrive as one semicolon-delimited string (`"PROTEIN: 0.00 GRAM; SODIUM: 7.14 MILLIGRAM; ..."`), not an array like the API gives. No explicit calorie/energy field.
  - Weight row: weight is in **grams**, not kg/lbs.
- **`Global Export Data/exercise-*.json`** — legacy Fitbit-format exercise sessions, paginated across ~23 files. Richer than the live API's `exercise` type: includes `logId` (stable, usable as a natural key), heart-rate zones, active-zone-minutes breakdown, GPS/pace/distance, and tracker device info.
- **`Health Fitness Data_GoogleData/UserSleeps_*.csv`, `UserSleepStages_*.csv`, `UserSleepScores_*.csv`** — **correction from an earlier pass**: these are split into several files by multi-year date range (e.g. `UserSleeps_2022-07-01.csv`, `_2023-07-01.csv`, `_2024-06-30.csv`...), not single all-history files. Each has its own stable ID (`sleep_id`, `sleep_stage_id`, `sleep_score_id`) and UTC timestamps with separate UTC-offset columns. `UserSleeps`' own "data_source" column reports the *recording method* (see above), not a device name, and has no device/app field at all. `UserSleepScores` is far richer than what's currently modeled as columns — see the `sleep_sessions` entry above for which sub-metrics got promoted vs. pushed into `raw_details`.
- **`Global Export Data/sleep-*.json`** — a second, legacy Fitbit-format sleep export (same shape family as `exercise-*.json`), with its own `logId`, an `efficiency` score (0-100, distinct from the CSV's 4-way score breakdown), and stage-level detail (`levels.data[]`) with **no per-stage ID** — confirms the live API isn't the only stage-ID-less source. Not yet decided which of the two Takeout sleep formats (this JSON, or the `UserSleep*` CSV family) the importer will actually parse — an implementation-time choice, not a schema one, since the schema already accommodates the union of both.
- Also present but not yet reviewed for modeling: `Sleep/Sleep Profile.csv`, `Sleep Score/sleep_score.csv` (a third sleep-score source), `Physical Activity_GoogleData/daily_sleep_temperature_derivations.csv`, and `respiratory_rate_sleep_summary_*.csv` — discovered while reviewing sleep, not yet inspected in detail.

## Open items

- **Multi-device step overlap** — confirmed via real data that two devices (e.g. a wearable and a phone) can independently report overlapping step activity, each internally consistent. Naively summing `steps_readings` rows for a daily total would double-count. Deliberately left as an app-logic decision (pick one authoritative `data_source_id` per user/metric when aggregating), not a schema change, alongside the other deferred reconciliation logic below.
- Whether the "drop if unmapped" ingest behavior (used for `lut_nutrient`) should also apply to `lut_meal_type`/`lut_data_source`/`lut_serving_unit`/`lut_activity_type`/`lut_measurement_type` — some of those are required fields on a required parent row, unlike an optional per-nutrient child row.
- Upsert priority, `mixed`-conflict resolution/recording, and the fingerprint-can-miss-a-time-edit edge case (native-ID-before-fingerprint doesn't help when *neither* source has a native ID) — all deferred to when the import/sync code is actually written. Full detail in the working plan history.
- `raw_details` JSON on `exercise_sessions`/`sleep_sessions` is intentionally unstructured for now; revisit if zone-level, GPS-level, or sub-score-level querying is needed later.
- Which raw Takeout sleep format (`UserSleep*.csv` family vs. the legacy `sleep-*.json`) the importer will actually parse — not yet decided, and several sleep-adjacent Takeout files (`Sleep Profile.csv`, a second `sleep_score.csv`, sleep-temperature and respiratory-rate summaries) haven't been inspected at all yet.
- Mapping raw activity-type codes (Takeout's numeric Fitbit `activityTypeId`, the API's string `exerciseType`) into canonical `lut_activity_type` rows is real reference-data work (Fitbit's own taxonomy has 100+ values) — deferred to ingest-time implementation, not attempted here.
- DB not yet created; `scripts/import-takeout.php` not yet built. See the note in `sql/schema.sql`'s header before running it (XAMPP/MySQL databases are created only with explicit confirmation, per project convention).
