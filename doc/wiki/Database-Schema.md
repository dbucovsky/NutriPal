# Database Schema

Defined in [`sql/schema.sql`](../../sql/schema.sql) (checkpoint — see status note below), with reference-data initialization in [`sql/init_lookups.sql`](../../sql/init_lookups.sql) and illustrative sample data in [`sql/sample_data.sql`](../../sql/sample_data.sql) (**stale** — still reflects the pre-redesign shape, see Open Items). General, project-agnostic schema patterns used throughout (naming, history/audit, ownership, non-destructive corrections) are documented separately in [[Database-Design-Patterns]] rather than repeated here — this page covers what's specific to NutriPal's own tables.

**Status**: the schema went through two real, full-scale import tests. The first, against a real ~3-year Google Takeout export, surfaced enough structural limitations in Takeout's data (see "Google Takeout export format" below) that **Google Takeout was dropped as an active ingestion source entirely** in favor of Android Health Connect (bulk history) plus the live Google Health API (incremental sync) going forward — Takeout's importer code and schema support are kept as a historical artifact, not deleted. The schema was then substantially redesigned (strict `food_log_entries` → `foods_db` reference model, `fingerprint` dropped everywhere in favor of `api_uid`-only identity, nutrient modifiers dropped in favor of versioning) and re-verified with a second full import against a real Health Connect export — see "Health Connect import findings" below. Cross-source reconciliation (upsert priority, `mixed`-conflict resolution) is now real for `sleep_sessions`/`exercise_sessions`/`measurements`; still open for `food_log_entries` — see Open Items.

**Two schemas**: `sql/schema.sql` creates and populates two databases — `nutripal` (every live/data table) and `nutripal_hist` (every `_hist` audit table, see [[Database-Design-Patterns]]) — so history, which grows much faster than live data, can be backed up/archived on its own cadence. **Before running this file against the real Bluehost database**, every `nutripal_hist` occurrence must first be replaced with the actual prefixed database name (Bluehost's cPanel prefixes all database/user names for this account, e.g. `theshaf2_nutripal_hist`) — the hist schema name is baked literally into every trigger body, since raw SQL can't parameterize identifiers. This is a manual step per deploy, documented in the schema file's header.

## Ingestion sources

NutriPal ingests health data from three possible sources, tracked via `ingestion_source_id` (→ `lut_ingestion_source`):
- **`health_connect`** — bulk import from an Android Health Connect SQLite export (`scripts/import-health-connect.php`). The current way to initialize a new user with full history.
- **`google_health_api`** — live incremental sync (last 7 days rolling, see [[Data-Sync]]). Not yet built (see Open Items).
- **`google_takeout`** — **deprecated, no longer an active source.** Kept in the lookup only so already-imported Takeout rows (from the schema's first real-data test) retain a meaningful provenance value. See "Google Takeout export format" below for why it was dropped.

Two more values exist:
- **`mixed`** — a genuine structural conflict between two sources for what identity resolution determined is the same logical entry. Now actually exercised: `sync-google-health.php`'s cross-source merge logic (see `doc/wiki/Data-Sync.md`) sets this when a `sleep_sessions`/`exercise_sessions`/`measurements` row already exists under one source and the other source reports a genuinely different non-`NULL` value for the same field (not just a field the first source never populated at all, which is a plain fill-in, not a conflict).
- **`nutripal`** — the row was created directly in the app (the future custom/repeat meal logging feature), not synced from any external source. Not named "manual" — Google's own `data_source` field already uses `MANUAL` for a different meaning (the user hand-entered data into the Fitbit/Google Health app itself).

**`data_source` vs. `ingestion_source` vs. `recording_method`** — three easy-to-confuse, deliberately disambiguated concepts: `data_source_id` (→ `lut_data_source`) is which app/device the source itself says recorded the entry (e.g. "Fitbit," a specific Android app name) — pass-through metadata, populated dynamically per row as new apps/devices are encountered. `ingestion_source_id` (→ `lut_ingestion_source`) is which of NutriPal's own ingestion pipelines wrote the row — our own bookkeeping, described above. `recording_method_id` (→ `lut_recording_method`) is *how* the reading was captured — `ACTIVELY_MEASURED`/`PASSIVELY_MEASURED`/`MANUAL`/`DERIVED` — mapped from Health Connect's `RecordingMethod` enum (`ACTIVELY_RECORDED`/`AUTOMATICALLY_RECORDED`/`MANUAL_ENTRY`/unknown). Present on `steps_readings`, `heart_rate_readings`, `heart_rate_variability_readings`, `daily_resting_heart_rate`, `measurements`, `exercise_sessions`, and `sleep_sessions` — nullable everywhere a source doesn't report it.

## Identity and deduplication

**`api_uid`** is now the sole DB-level identity/dedup mechanism, on every table that has it — there is no `fingerprint` column anywhere in the schema. This was a deliberate simplification: the original fingerprint scheme existed mainly to dedup Takeout re-imports and cross-check Takeout against the API, and once Takeout was dropped as an active source that need mostly went away. Health Connect gives every record a genuine `uuid` (a real native ID, unlike most of Takeout's CSV formats which had none at all), so `api_uid` (`UNIQUE(user_id, api_uid)`, nullable-safe) is sufficient for its rows.

**`steps_readings`, `heart_rate_readings`, `heart_rate_variability_readings`, and `sleep_stages` all now have a real DB-level natural-key guard**, closing a gap that used to mean these four tables relied on Health Connect's per-row `uuid` (present for steps/HRV, absent for heart-rate/sleep-stages — see below) plus, for live-API-inserted rows only, application-level in-memory dedup with no DB-level backstop. That backstop mattered: a `--full` live sync deliberately skips its in-memory timestamp preload (holding millions of timestamps in PHP memory isn't practical), so a `--full` run against a non-empty table had nothing stopping a plain `INSERT` from duplicating already-present rows. Confirmed as a real, not just theoretical, bug twice — a same-source Health Connect re-import duplicating every heart-rate reading (5,712,042 rows where only 2,856,973 were distinct), and separately an interrupted `--full` live sync duplicating ~138,000 `steps_readings` rows. Fixed with real natural-key constraints: `UNIQUE(user_id, reading_time)` on `steps_readings`, `heart_rate_readings`, and `heart_rate_variability_readings`; `UNIQUE(user_id, sleep_session_id, stage_type_id, start_time)` on `sleep_stages` (session + stage type + start time, since stages have no per-row identity of their own even from Health Connect). `INSERT IGNORE` (already used everywhere these tables are written) now genuinely dedupes regardless of source. See `doc/wiki/Data-Sync.md`'s "Two more real bugs" and "A fourth bug, and an unexplained incident" sections for the full story, including a related bug this uncovered in the sleep-session dedup lookup and a crash this caused in `sync-google-health.php`'s `--full` mode (fixed with `INSERT IGNORE`).

**`sleep_sessions`, `exercise_sessions`, and `measurements` also now have a real natural-key guard specifically for cross-source duplication**, on top of their already-working `UNIQUE(user_id, api_uid)` (real and effective for same-source re-imports, since both sources give these a genuine native id — that part was never broken). The gap was cross-source: Health Connect and the live API assign different `api_uid`s to the same real event, so that constraint alone can't recognize a session/reading already exists from the other source. Confirmed via real data: 660/710 HC sleep sessions, 1980/2015 HC exercise sessions, and 513/521 HC weight readings each matched a live-API row on timestamp alone. Fixed with `UNIQUE(user_id, start_time)` on `sleep_sessions`/`exercise_sessions` and `UNIQUE(user_id, measurement_type_id, reading_time)` on `measurements`, plus a cross-source check in `sync-google-health.php`'s `upsertByNaturalKey()`: a hit on the natural key (but not on `api_uid`) means the other source already has it, so the row is skipped rather than inserted or updated — updating would silently overwrite that source's provenance and, for measurements, its more-precise value (HC rounds to 100g, the live API keeps single-gram precision, so `value` deliberately isn't part of the key). `food_log_entries` still has only `UNIQUE(user_id, api_uid)` — cross-source duplication there is unresolved and structurally harder, since the same real meal usually resolves to a *different* `food_id` between sources (confirmed: only 122 of 13,094 same-`start_time` cross-source pairs also share a `food_id`). See `doc/wiki/Data-Sync.md`'s "Cross-source duplication for sleep, exercise, and weight/height" section for the full story.

## Tables

**Food log — strict reference model** (redesigned; see [[Database-Design-Patterns]] for the general non-destructive-correction pattern):
- `food_log_entries` — one row per logged food event, always referencing exactly one `foods_db` row: `food_id`, `serving_amount` (a multiplier), and `serving_unit_id` (→ `lut_serving_unit`) are all `NOT NULL`. No nutrition data lives on this table at all — it's always derived by joining through `food_id` into `foods_db`/`foods_db_nutrients`, scaled by `serving_amount`. This replaced an earlier design that duplicated `food_name`/`energy_kcal`/`total_protein_g`/etc. directly on the log row; the duplication made "is this really the same food, or a new one" ambiguous and was dropped once the redesign clarified that a log entry's only job is "which catalog food, and how much." `start_time`/`end_time` always differ by exactly 1 minute for Google-sourced data — not a real duration, just how the source's interval-shaped data model represents a single moment. `ingestion_source_id`/`data_source_id`/`api_uid` live on this table (provenance of a logging *event*), not on `foods_db` (a property of a *food*) — see [[Database-Design-Patterns]]. Logging is always at ingredient level, matching how Google itself logs (separate rows per item eaten, never one row per composed meal) — a "recipe" (a home-cooked meal's ingredient list, entered once and reused) is a deliberately separate, not-yet-built concept that a log entry never references directly; the log always records what was actually eaten, ingredient by ingredient.

**`foods_db` family** — the user's own + historically-encountered food catalog, motivated by how the user actually eats (mostly home-cooked, buying ingredients in bulk and eating them across several meals) and by neither Google source exposing a way to search existing food data — only what's already been logged is visible:
- `foods_db` — nutrition always normalized per 100 units of the food's `dimension` (100g or 100mL), matching label convention. Three-tier ownership (universal / group / user) via `group_id`/`user_id`. `version` tracks that the same food name can legitimately have multiple real nutritional variants over time (different products, reformulations, or genuinely different recipes for a home-cooked dish) — `NULL`/`0` is the original version, incrementing from there; a food with no sibling versions shows no version label in the UI. **No DB-level uniqueness constraint on `(name, brand_name)`** — `idx_foods_db_name` is a plain lookup index only. This was a deliberate loosening: whether two rows with the same name are "the same food" isn't a fact the database can verify (precision noise must not create a spurious version; a real recipe change should), so matching logic (see "The quantity problem" below) lives entirely in application code, not a unique constraint.
- `foods_db_custom_units` — per-food named units beyond the universal standard ones (e.g. "small/medium/large orange," "18in pie slice," or an importer-created placeholder like "reported serving" — see below), one of which can be flagged `is_default`. Tied to one specific `foods_db` row (one version) — not automatically shared across other versions of the same food.
- `foods_db_nutrients` — one row per nutrient per food (version): `nutrient_id` → `lut_nutrient` (deliberately curated — a nutrient not already in the lookup is dropped at ingest, not auto-added), `quantity`, `unit_id` → `unit_conversions`. No more `SRC`/`FIX`/`MOD` value types — that modifier system was dropped entirely; a real correction to a nutrient value now creates a new `foods_db` version instead of a competing override row, keeping "what is this food's nutrition" a single unambiguous fact per version rather than several competing claims resolved at read time.
- `foods_db_last_used` — per-`(user, food)` usage tracking, kept separate from `foods_db` to isolate high-churn writes. `score` is a bounded, self-decaying recency-weighted frequency — see [[Database-Design-Patterns]] for the write-time decay algorithm.
- `unit_conversions` — universal mass/volume unit conversions, shared by both `foods_db` and nutrient quantities.
- `lut_serving_unit` — resolves a logged serving unit to either a standard `unit_conversions` row or a food-specific `foods_db_custom_units` row. `lut_serving_unit.label` is an internal technical key only (embeds the food id and source prefix, e.g. `api_951_gram`, `hc_reported_serving_266`) — never meant for display. The real human-readable name is `unit_conversions.name` or `foods_db_custom_units.unit_name`, whichever the row resolves to (fixed in V0.1.10 after the food log UI was found displaying the raw technical label).

**The quantity problem (and its fix)**: Health Connect's `nutrition_record_table` reports absolute nutrition totals for "however much was eaten," with no separate serving/mass field at all — so two log entries for genuinely the same food at different amounts show up as two different absolute numbers, indistinguishable at the schema level from two different foods. Confirmed concretely during the real import: "Yellow Onion" initially produced 41 near-duplicate `foods_db` versions that were actually the same onion at ~41 different unknown quantities (clean multiples of one another, e.g. 9/18/13.5/36/45/54 kcal). Fixed in `findOrCreateFood()` (`scripts/import-health-connect.php`) with **ratio-based matching**: for every existing `foods_db` version sharing the incoming food's name, compute the implied scale factor between the incoming and existing energy/protein/carb/fat values; if those ratios agree with each other (within 15% of their median), it's the same food at a different amount — reuse that `food_id`, with the derived ratio becoming `serving_amount`. A new version is only forked when no existing version's ratios are internally consistent. The quantity itself is expressed via a per-food placeholder custom unit ("reported serving," `equivalent_amount = 100`, matching the per-100 storage convention) rather than a guessed real gram weight; every `food_log_entries` row referencing it (`serving_amount` is a pure ratio) stays correct with zero historical rewrites, since the real total is always `serving_amount × equivalent_amount`. Verified on the real re-import: max versions for any one food name dropped from 41 to 4 (the remaining multi-version foods, e.g. "Cream Cheese" ×4, look like genuine product variation, not the quantity artifact).

**This placeholder-to-real correction is now actually implemented** (`doc/wiki/Data-Sync.md`'s "Reconciling placeholder food versions with real-gram data"), and it's not *just* the custom unit row that needs updating: `foods_db`'s own macro columns store the *raw reported values*, not per-100g, for a placeholder row — leaving `equivalent_amount` at its old nominal `100` while changing it to the real gram weight would silently corrupt the round-trip (`serving_amount × equivalent_amount ÷ 100 × macro`) for every entry that already references it. The real fix instead migrates affected `food_log_entries` rows onto the already-correct real-gram `foods_db` row (re-expressing `serving_amount` in real grams) and leaves the placeholder permanently orphaned rather than editing it in place — `foods_db` can't be `DELETE`d (`trg_foods_db_bd`), and a stray unreferenced placeholder is harmless. A UI to review the smaller number of foods still stuck on a placeholder with no real-gram counterpart yet (edit a food's unit, search for one to fix, or a post-import "new foods" review list) is still planned but not built.

**Steps & heart rate** — simple timestamped readings, each with its own `data_source_id`/`recording_method_id`/`ingestion_source_id`/`api_uid` cluster (no dedup guard for the three high-volume series tables, see above):
- `steps_readings` — incremental step counts. Multiple devices can independently report overlapping activity — naively summing all rows for a daily total would double-count (see Open Items).
- `heart_rate_readings` — continuous point-in-time bpm samples. Health Connect splits this into a parent "session" table (device/app/recording-method context) and a child series table (individual timestamped samples) — the importer joins them so every reading still carries full context.
- `heart_rate_variability_readings` — RMSSD in milliseconds, a distinct, much-lower-sample-rate metric from continuous bpm.
- `daily_resting_heart_rate` — one value per calendar day, keyed by `(user_id, reading_date)`. **Not imported from Health Connect this pass** — whether HC can report more than one resting-HR figure per day, and how that would need to be deduped, was left an open question (see Open Items) rather than guessed at.

**`measurements`** — a single generic table for point-in-time scalar body metrics (weight, height, blood pressure, body fat %, etc.): `measurement_type_id` (→ `lut_measurement_type`), `value`, `unit_id` (→ `unit_conversions`). Weight is stored in grams; height is stored via a length unit — **Health Connect reports height in meters**, confirmed directly against real data (`height = 1.70179998874664`) before writing any import code, avoiding what would otherwise have been a silent 1000x unit bug if millimeters had been assumed by analogy with the column name.

**`exercise_sessions`** — core fields as columns (`activity_type_id` → `lut_activity_type`, currently a plain find-or-create keyed on each source's raw activity code rather than a true canonical mapping — see Open Items; `distance_unit_id` → `unit_conversions`; `has_gps`). `api_uid` (Health Connect's `uuid`, or the live API's own id) identifies a row within its own source — the earlier Takeout-specific `log_id` column was removed once Takeout was dropped — plus a real `UNIQUE(user_id, start_time)` natural key for catching the same session arriving from *both* sources (see "Identity and deduplication" above). **Known Health Connect limitation**: `exercise_session_record_table` has no calories/distance/steps/average-heart-rate columns at all (Health Connect stores those in separate generic time-series tables with no foreign key back to the session) — these four columns are left `NULL` for a Health-Connect-only session, but get filled in after the fact by the live sync's cross-source merge (see `doc/wiki/Data-Sync.md`) if the live API ever reports the same real session. GPS route points are not imported, only a `has_gps` flag. Heart-rate zones and active-zone-minutes breakdown remain in a `raw_details` JSON column, not normalized.

**`sleep_sessions`** + **`sleep_stages`**: drastically simplified from the pre-redesign draft. `sleep_type_id` (→ `lut_sleep_type`, `CLASSIC`/`STAGES`) and `main_sleep` are now **nullable** — Health Connect has neither concept at all, unlike Takeout. Every score/duration-breakdown column from the earlier draft (`overall_score`, `duration_score`, `composition_score`, `revitalization_score`, `minutes_asleep`, `minutes_awake`, `efficiency`, `resting_heart_rate`, and the `raw_details` JSON column) was **removed entirely** — confirmed Health Connect's `sleep_session_record_table` has no score columns and no way to derive them, and once Takeout (the only source that ever had scores) was dropped, keeping those columns would mean permanently-`NULL` dead weight. `sleep_stages` keeps `api_uid` (nullable) since neither source provides a genuine per-stage native ID, but it's not the table's real duplicate guard — see "Identity and deduplication" above for `UNIQUE(user_id, sleep_session_id, stage_type_id, start_time)`, the constraint that actually catches a re-import.

**Multi-user readiness** (schema shape only — no login/registration UX exists yet; the app still just operates as one hardcoded user): `users`, `groups`, `link_user_group` (membership + per-user group-priority ranking). Every user-owned table carries `user_id` directly, including child tables, and every uniqueness constraint is scoped per-user. Full rationale in [[Database-Design-Patterns]].

**`users.birth_date`/`gender_id`** (2026-09-10, `gender_id` → new `lut_gender`) are the app's first real user-editable profile fields (via `public/api/profile.php` / the frontend Settings panel), both nullable since neither is collected at signup. `birth_date` backs the age-based Max HR estimate below; `gender_id` is captured on the profile per request but not currently consumed by any formula.

**Max HR has three independently-tracked sources** (age estimate, observed-from-sessions, manual override), all always computed regardless of which is active. Which one is "effective" is a plain preference, `users.max_hr_source_id` → new **`lut_max_hr_source`** (`age`/`observed`/`manual`, fixed seeded ids 1/2/3 — same hardcode-the-small-closed-vocabulary-client-side pattern as `lut_gender`), not an automatic priority order — see `src/MaxHeartRate.php` for the read/write logic and the one documented fallback (to `age`, if the preferred source currently has no value).

- **`max_heart_rate_history`** — every age-estimate or manual-override value a user has ever had, one row per change, `UNIQUE(user_id, effective_date)`, current value = the row with the latest `effective_date`. Deliberately **does not** follow this schema's usual `_hist`-companion-plus-trigger pattern (see [[Database-Design-Patterns]]) — that pattern exists to preserve a row's pre-update state, and nothing here is ever updated in place; every birthday recompute or override is a brand new fact, appended, never correcting an earlier row. Still gets a `BEFORE DELETE` blocker trigger, matching this schema's blanket "nothing is ever destroyed" rule, even though the app itself never issues a delete against it. No cron job involved; a birthday recompute happens lazily, checked on whatever request next reads the age estimate. Switching the preference away from `manual` no longer erases anything — with three coexisting sources there's no "reset to computed" action any more, the override row just sits unused until the preference is switched back.
- **`exercise_sessions.observed_max_hr_estimate`** (`SMALLINT UNSIGNED NULL`, placed right after `average_heart_rate`) — one estimate per qualifying session (running/treadmill/aerobics-type activities only, matched by `lut_activity_type.name`; not walks or generic workouts), computed from raw `heart_rate_readings` and filled in **lazily on read**, not at insert time. The value itself is a **sustained** peak, not the single highest raw reading: `MaxHeartRate::sustainedPeakBpm()` takes the highest rolling-median bpm over any 120-second window in the session, divided by 0.95 — a plain `MAX(bpm)` was tried first and rejected once real testing showed a single sensor glitch (one reading spiking far above its neighbors) could inflate the whole estimate off one bad sample; a median is robust to exactly one such outlier per window while a genuinely sustained hard effort still comes through. This was a deliberate change from the original "compute live while inserting the session" idea: `scripts/sync-google-health.php` inserts `exercise_sessions` before `heart_rate_readings` in every run (including `--full`), so a peak-HR lookup at insert time would almost always find nothing yet, while `scripts/import-health-connect.php` inserts heart rate first — the two scripts disagree, so an insert-time hook couldn't be made reliable across both. Follows `exercise_sessions`' own history rules exactly like any other column there — present on `exercise_sessions_hist` and copied by `trg_exercise_sessions_bu`, since it's a value that genuinely can be filled in later by an in-place `UPDATE`, unlike `max_heart_rate_history` above.

  The observed estimate reported to the app is the `MAX(observed_max_hr_estimate)` over a trailing 21 days, backfilled just-in-time by `MaxHeartRate.php`. There are two distinct callers: the Settings panel just wants "today's" value, backfilling only the last 21 days; `exercise.php` needs the value **as of each session's own date** (so an old session is zone-classified against the estimate that was true back then, not today's - the estimate drifts, so applying today's number everywhere was a real bug, since fixed), which backfills every qualifying session across the whole requested range and computes a separate trailing-21-day max ending on each date. Either way it's self-limiting: a session that can never get HR data simply stops being rechecked once nothing still asks about that time range.

**`faq_entries`** (2026-09-10) — app content, not user health data: one row per FAQ question, shown on the standalone FAQ page reached from the menu's Help submenu (see `doc/wiki/Architecture.md`). `question`/`answer` are `TEXT` columns holding **Markdown**, not raw HTML — rendered client-side via `marked` rather than trusting stored HTML directly, and simpler to hand-author/edit a row's content straight in the DB. `display_order` is a plain sort key (not a date/priority column). Gets the schema's standard `_hist`-companion-plus-trigger treatment (`faq_entries_hist`, copy-on-update, block-delete) like any other regular content table — unlike `max_heart_rate_history` above, a FAQ entry's content genuinely is corrected in place (a typo fix, a reworded answer), so preserving the pre-edit version on update is the right pattern here, not the append-only one. Not user-owned — no `user_id` column, since this is the same content for every user of the app.

## Health Connect export format (observed, 2026-09-08)

An Android Health Connect export is a single SQLite database with 78 tables, properly relational via `app_info_id`/`device_info_id` foreign keys into `application_info_table`/`device_info_table` — a genuinely different shape from Takeout's per-format CSV/JSON files. Facts confirmed directly against a real export before writing import code (not assumed):

- Every record type has a genuine `uuid` (16-byte BLOB) — a real native ID, unlike most Takeout formats.
- `start_zone_offset`/`end_zone_offset` (seconds) give explicit timezone context per record.
- Units, verified against real rows rather than assumed: weight in grams (matches the existing convention); **height in meters** (not millimeters — see the `measurements` note above); nutrition macro/micronutrient columns uniformly in grams; the `energy` column is in "calories," not kilocalories (divide by 1000 for kcal — confirmed via plausibility check: "Large Eggs" `energy=189000` → 189 kcal).
- `RecordingMethod` enum: 0=UNKNOWN, 1=ACTIVELY_RECORDED, 2=AUTOMATICALLY_RECORDED, 3=MANUAL_ENTRY.
- `MealType` enum: 0=UNKNOWN (mapped to `ANYTIME`), 1=BREAKFAST, 2=LUNCH, 3=DINNER, 4=SNACK.
- `SleepStageType` enum: 1=AWAKE, 2=SLEEPING (generic, mapped to `ASLEEP`), 3=OUT_OF_BED (mapped to `AWAKE`), 4=LIGHT, 5=DEEP, 6=REM, 7=AWAKE_IN_BED (mapped to `AWAKE`), 0=UNKNOWN (mapped to `UNSPECIFIED`).
- `nutrition_record_table` has no serving/quantity/mass column at all — see "The quantity problem" above.
- `exercise_session_record_table` has no calories/distance/steps/avg-heart-rate columns — see the `exercise_sessions` note above.
- `sleep_session_record_table` has no score columns and no `sleep_type` concept at all.
- Heart rate is split into a parent `heart_rate_record_table` (session/batch, device/app context) and a child `heart_rate_record_series_table` (individual samples) — no such split for HRV, which is a single flat table.
- `activity_intensity_record_table` (Android's newer zone-like concept) exists in the schema but had **zero rows** in the real export inspected — not usable as an alternative to zone/active-minute data yet.
- Multiple apps can write to the same Health Connect database (12 distinct `app_info_id` values observed in the real export) — `data_source_id` is resolved dynamically per row from `application_info_table`, same as Takeout's per-row device/app strings.

## Google Takeout export format (observed, 2026-09-05 — historical, no longer imported)

Kept for reference since already-imported Takeout rows exist in the database and this shaped the decision to drop it as an active source. A Takeout "Google Health" export unpacks into several differently-shaped areas — not one uniform format:

- **`Physical Activity_GoogleData/`** — one folder of per-month CSVs per data type: `steps_YYYY-MM-DD.csv`, `heart_rate_YYYY-MM-DD.csv`, `distance_...`, etc. Each row is just `timestamp, value, data source`. `nutrition_log.csv` and `weight.csv` are exceptions — single all-history files, not split by month.
  - Nutrition row: `start time, end time, brand name, food name, meal type, nutrients, data source` — nutrients arrive as one semicolon-delimited string, not an array. **No serving/quantity field, no energy field, and no explicit ID column** — several structural gaps that Health Connect (uuid-based identity, at least *some* per-record structure) improved on, even though HC has its own gaps (see above).
  - Weight row: weight is in grams.
- **`Global Export Data/exercise-*.json`** — legacy Fitbit-format exercise sessions. Includes `logId` (a real native ID — one of only two Takeout categories that had one), heart-rate zones, active-zone-minutes breakdown, GPS/pace/distance.
- **`Health Fitness Data_GoogleData/UserSleeps_*.csv`, `UserSleepStages_*.csv`, `UserSleepScores_*.csv`** — the other Takeout category with real native IDs (`sleep_id`, `sleep_stage_id`, `sleep_score_id`). `UserSleepScores` was far richer than anything Health Connect can provide (0-100 composite scores, sub-scores) — this was Takeout's main advantage and the main tradeoff accepted by dropping it.
- **Real, decisive findings from the original full Takeout import** that contributed to the decision to move off it: nutrition's literal `"N/A"` sentinel string (~21% of values) required special handling to avoid silently corrupting values to zero; carbohydrates were present in only ~16% of rows and, when present, were *always* `"N/A"` (never a real usable number); total fat was never reported at all — meaning any energy estimate derived from macros was structurally unreliable for a large fraction of entries. This nutrition-data-quality gap (not present in the same form in Health Connect, which always reports usable absolute macros) was one of the deciding factors for nutrition specifically.
- Also present but never inspected in detail: `Sleep/Sleep Profile.csv`, `Sleep Score/sleep_score.csv` (a third sleep-score source), sleep-temperature and respiratory-rate summaries.

## Health Connect import findings (2026-09-08 full re-import)

Running `scripts/import-health-connect.php` against a real Health Connect export, after the schema redesign, as the official end-to-end test:

- Zero errors across every category. Final counts: 220,237 steps readings; 2,854,655 heart-rate readings; 22,036 HRV readings; 710 sleep sessions / 33,121 stages; 2,015 exercise sessions; 520 weight / 1 height reading; 2,376 nutrition log entries resolving to 583 catalog foods (531 distinct names).
- Two real bugs were found and fixed by actually inspecting results, not by trusting a clean-looking log: `PDOStatement::fetch()` returning `false` (not `null`) on no match was silently producing wrong version numbers for brand-new foods; and catching the entire SQLSTATE `23000` class (rather than MySQL's specific error code 1062 for a duplicate key) mislabeled a real foreign-key failure — a missing `lut_serving_unit` seed row for `'gram'` — as "2,376 duplicates," silently zeroing out `food_log_entries` with no visible error in the log.
- The quantity problem (see above) was found the same way — by querying `foods_db` directly after a clean-looking import and noticing "Yellow Onion" had 41 versions, not by anything the log surfaced on its own.

## Open items

- **Multi-device step overlap** — two devices can independently report overlapping step activity, each internally consistent. Naively summing `steps_readings` rows for a daily total would double-count (confirmed directly: one real day has two sources reporting 16,830 and 6,380 steps for the same day). `public/api/steps.php` (2026-09-10) works around this for display purposes — per day, use whichever single `data_source_id` reported the most steps that day, discard the rest — but this is a disclosed heuristic, not the real fix (a proper natural-key cross-source merge, like `sleep_sessions`/`exercise_sessions`/`measurements`/`food_log_entries` got, is still undone).
- Upsert priority and `mixed`-conflict resolution are now real and exercised for `sleep_sessions`/`exercise_sessions`/`measurements`/`food_log_entries` (see `doc/wiki/Data-Sync.md`) — first-recorded source stays authoritative, the other source's genuinely new fields get merged in, and a real value conflict sets `mixed`.
- `sql/sample_data.sql` is stale — still reflects the pre-redesign shape (`food_name`/`brand_name` on `food_log_entries`, `food_log_nutrients`, `SRC`/`FIX`/`MOD`) and needs a rewrite or retirement.
- `lut_activity_type` still isn't a real canonical mapping — both importers do a plain find-or-create keyed on each source's raw activity code (Takeout's numeric Fitbit `activityTypeId`, Health Connect's `exercise_type`), so each raw code becomes its own row rather than resolving to a shared canonical activity type across sources.
- `daily_resting_heart_rate`'s multiple-readings-per-day question (whether Health Connect can report more than one per day, and how to dedup if so) is unresolved — no `api_uid` was added, and the table wasn't populated from Health Connect this pass.
- A UI to correct the quantity-problem's placeholder "reported serving" custom units (edit a food's unit directly, search for a specific food, and a post-sync/import review list of every food still on the placeholder) is planned but not designed in detail yet.
- Matching catalog foods against a real reference nutrition database (e.g. USDA FoodData Central) for true gram-accurate quantities, rather than the placeholder unit, is a bigger future integration — not attempted.
- The "recipe" concept (a home-cooked meal's ingredient template, reused across multiple log entries without the log ever referencing the recipe directly) is a deliberately separate, not-yet-designed feature.
- Build the live-API-to-database sync — currently only bulk importers write to the database.
